# 两套视觉实现并存，合成稿是派生视图

演示（React）与合成稿（HTML/GSAP）各司其职：演示是**视觉决策与验收**的唯一场所，合成稿是**渲染用派生视图**。两者共享 `beats.json`（由 `narrations.ts` + ffprobe 生成）作为节拍、音频与时长的唯一账本，共享视觉原子（类名 + 必填 DOM 外壳 + `.in/.lit/.dim` 状态类）作为样式契约；合成稿的骨架由生成器产出，身体与挂载钩子手写。演示的章节代码与合成稿的身体仍是两份代码，这是明知代价的选择。

## 为什么不是一套

- 只留合成稿：第 1 章的验收对象消失（没有可点的演示），且每次迭代要看 137 秒渲染结果，反馈从秒级退化到分钟级。
- 只留演示（React 组件共享）：合成稿是静态 HTML，无法 import JSX；共享只能停在 CSS + DOM 契约这一层。
- 让合成稿身体自动导出：React 章节是 `step` 函数而非可序列化 DOM，技术上不成立。

## 后果

- `data-start` / 时长 / 音频文件全部由账本累加得出，手写秒数在结构上被排除；旧样例的静音与旁白错位正是手写秒数 + 两套编号的产物。
- 结构漂移可被 `check` 挡住（节拍数、音频引用、时长、钩子声明），**视觉漂移挡不住**，只能靠渲染后的联系表 + 抽查帧人工复审。
- 视觉原子必须是契约而非实现：只暴露状态类，动画实现（CSS keyframes / GSAP）由两端各自负责，否则共享只是把重复的 CSS 换成重复的动效。
- 视觉原子需要自己的回归面（atoms 画廊页，每个原子 × 三种状态），否则契约会悄悄腐烂。
